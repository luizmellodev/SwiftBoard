SwiftBoard

A runtime component gallery. You register scenarios (a component + a named state) in your own Swift code; this site is a live view of whatever is currently registered in the running process — nothing is generated ahead of time, and nothing is stored on disk unless you explicitly export it.

What you actually need (no folder rules)

SwiftBoard does not care where files live, how they are named, or whether you have a “design system package.” There is no special folder and no required filename. The site is generated at runtime from whatever you registered in the running app.

You only do two things:

  1. Register — call SwiftBoard.shared.addScenarios(...) with a SwiftUI view (any view: a Button, your MeuBotao, whatever). That can live in the component’s own file or in one BoardScenarios.swift. Optional: pass summary, parameters, and docs: ScenarioDocs(snippet:) so the board shows API copy.
  2. Start the server — once, at app launch, behind #if DEBUG: 
    #if DEBUG
.task {
    BoardScenarios.registerAll() // or addScenarios directly
    try? await BoardServer().start()
}
#endif

Run the app (⌘R). The console prints http://127.0.0.1:8080. That URL is the site. Stop the app and the site goes away (unless you StaticExporter.export).

Building your own design system = normal SwiftUI views, anywhere in the target. SwiftBoard is only the gallery. Using SwiftDS instead = add that second package and copy Examples/SwiftDSCatalogRegistrar.swift, which already calls addScenarios for you.

Where does the code go? (App.swift vs elsewhere)

Something in the running process has to call BoardServer().start() or there is no website. In an iOS/macOS app that is almost always the @main App (often YourApp.swift / App.swift), on the root view, behind #if DEBUG:

@main
struct MeuApp: App {
    var body: some Scene {
        WindowGroup {
            ContentView()
            #if DEBUG
                .task {
                    BoardScenarios.registerAll()
                    try? await BoardServer().start()
                }
            #endif
        }
    }
}

That .task is the only thing that must sit on the app entry point. You do not put every component in App.swift.

  • BoardScenarios.swift (any name, any folder in the app target) — registerAll() that calls addScenarios, or
  • each component file, via BoardScenarioProvider, and registerAll() only lists the types.

If you skip the .task in the App struct, nothing starts the server — the gallery files can exist and still never appear as a site.

You do not need SwiftDSCatalogRegistrar.swift unless you are using SwiftDS. That ~300-line file only exists to map SwiftDS’s catalog + showroom into addScenarios. For a design system you write yourself, a small BoardScenarios.swift (or providers on each component) is enough — often under 30 lines to start. You also do not have to change ContentView; the test app only added a DEBUG label with the URL, and that is optional.

The usual pattern (one component + the list)

Three steps. The view does not import SwiftBoard. Only the DEBUG extension does.

1. The component — states live next to the view, like a #Preview:

import SwiftUI

struct AppButton: View {
    let title: String
    var body: some View {
        Button(title) {}.buttonStyle(.borderedProminent)
    }
}

#if DEBUG
import SwiftBoardServer

extension AppButton: BoardScenarioProvider {
    static func provideScenarios(into board: SwiftBoard) {
        board.addScenarios(
            category: "Actions",
            component: "Button",
            summary: "Primary tappable action.",
            parameters: [
                ScenarioParameter(name: "title", type: "String")
            ]
        ) {
            Scenario("Primary", docs: ScenarioDocs(snippet: "AppButton(title: \"Continue\")")) {
                AppButton(title: "Continue")
            }
            Scenario("Disabled") {
                AppButton(title: "Continue").disabled(true)
            }
        }
    }
}
#endif

That addScenarios is this component only. Extra Scenario(...) blocks are states (Primary, Disabled), not more components.

2. The list — one line per component. It does not grow with every state, only when you add a new type. Small DS = tiny file; 80 components = 80 lines of .self, not 80 copies of the preview:

#if DEBUG
import SwiftBoardServer

enum BoardScenarios {
    @MainActor
    static func registerAll() {
        SwiftBoard.shared.addScenarios(from: [
            AppButton.self,
            AppBadge.self,
        ])
    }
}
#endif

3. App.swift — start the server (see above). Then ⌘R and open the URL.

Getting started

1. See it working (zero setup). This repo already has a working demo you can run before writing anything:

cd SwiftBoard
swift run SwiftBoardDemo

Wait for the status text to say Running at http://127.0.0.1:8080, then open that URL — that's this exact site, showing the demo's example components. (Have SwiftDS checked out as a sibling? From this repo, cd Examples && swift run SwiftBoardKitDemo shows the same thing with a real design system. That Examples package is not part of the published SwiftBoard product.)

2. Point it at your own components. Once you've seen it work:

  • Already have an app? Add SwiftBoardServer as a dependency, write one file that calls SwiftBoard.shared.addScenarios(...), and call it plus BoardServer().start() from your app's startup code behind #if DEBUG. Run your app as usual and open the URL from the console.
  • Nothing yet, just trying this out? swift package init --type executable in a new folder, add SwiftBoardServer as a dependency, put the two calls above in main.swift followed by RunLoop.main.run(), then swift run.

See this repo's README.md for the exact code for both paths. That one-file example is for getting a single component on screen — once you have more than a couple, see "Creating a new component / state" below for a pattern that scales to a whole design system without growing one giant file.

On a real iOS device (not needed on the Simulator or macOS): BoardServer listens on all interfaces, not just loopback, so add NSLocalNetworkUsageDescription to your app's Info.plist (any string explaining why) — without it, iOS may block the first connection instead of serving it.

FAQ

I'm starting a brand-new project and want to build my own design system from scratch. Create your app, add SwiftBoardServer as a dependency, build your components as normal SwiftUI views, and conform each one to BoardScenarioProvider right in its own file (see "Creating a new component / state" below). Register + start behind #if DEBUG. This is the most tested path — it's exactly what SwiftBoardDemo in this repo does.

I want to start from a complete, ready-made design system instead of building one from scratch. Add two packages: SwiftBoardServer from SwiftBoard, and SwiftDS from SwiftDS. Copy Examples/SwiftDSCatalogRegistrar.swift into your app and call SwiftDSCatalogRegistrar.registerAll(). SwiftBoard will not download SwiftDS for you. To later change a component's actual appearance, you need your own copy of SwiftDS (a fork).

Does that mean I need two package dependencies — SwiftBoard and SwiftDS? Yes, if you want the SwiftDS catalog. If you are building your own design system, add only SwiftBoard.

Does SwiftDS have to import SwiftBoard? No. SwiftDS stays independent. BoardScenarioProvider lives in your app (or in a design-system package that already depends on SwiftBoard). A third-party DS that must not know about SwiftBoard is registered from the app with a loop over its catalog (see SwiftDSCatalogRegistrar) — that file is glue in the app, not a change to SwiftDS.

Does SwiftBoard automatically find every SwiftUI view in my project? No. It only shows what you addScenarios. There is no folder scan and no “all View types” discovery — a View is just a type; the board cannot know which ones are design-system components or which states to screenshot. You register each component (or each state), the same way you add a #Preview. To avoid one giant file, use BoardScenarioProvider on the component and a one-line list in registerAll(). If you already have a data catalog (like SwiftDS’s DSComponentCatalog), one loop can register everything — that is what SwiftDSCatalogRegistrar is, not a SwiftBoard built-in.

I already have an app that doesn't use any design system — will adding SwiftBoard break anything, error, or crash? No — it's purely additive: one new file plus a few lines in your app's startup code, behind #if DEBUG. To roll it in gradually: add the dependency and build (nothing to break yet) → register one scenario wrapping a view you already have → start the server from a .task behind #if DEBUG, testing in the Simulator first → confirm the URL shows that one component → add the rest of your views one at a time → only then try a physical device and add NSLocalNetworkUsageDescription.

Does this actually work on iOS, or only macOS? The core library (and FlyingFox, the HTTP server it uses) compiles cleanly for iOS. The two demo apps bundled in this repo are macOS-only (they use AppKit to open a window and a browser) — that's a limitation of the demos, not of SwiftBoard itself. BoardGallery uses only cross-platform SwiftUI and works on iOS today.

Where does this code live — my app, or a separate package?

Either. SwiftBoard doesn't require a specific project layout — it only cares that SwiftBoard.shared.addScenarios(...) gets called before BoardServer().start(). Two common setups:

  • No separate design-system package: add the SwiftBoard package as a dependency of your app, write your scenario registrations in a small file (e.g. BoardScenarios.swift) compiled only in DEBUG, and call BoardServer().start() from your app's startup code behind #if DEBUG. Nothing new to create.
  • You already have (or want) a separate design-system package — like SwiftDS: that package does not need to know SwiftBoard exists. Your app depends on both, copies Examples/SwiftDSCatalogRegistrar.swift (or writes an equivalent bridge), registers components, and starts the server.

Creating a new component / state

Call addScenarios anywhere that runs before the server starts:

SwiftBoard.shared.addScenarios(category: "Actions", component: "Button") {
    Scenario("Primary") {
        Button("Continue") {}.buttonStyle(.borderedProminent)
    }
    Scenario("Disabled") {
        Button("Continue") {}.buttonStyle(.borderedProminent).disabled(true)
    }
}

Each Scenario is one state/card on the site. Calling addScenarios again for the same category/component appends more states to it. Don't pile every component into one file as your design system grows, though — two ways to keep it manageable:

  • Co-located, one file per component (recommended default). Conform the component's own type to BoardScenarioProvider, right in the file where it's already defined — like a #Preview block: 
    extension DemoButton: BoardScenarioProvider {
    static func provideScenarios(into board: SwiftBoard) {
        board.addScenarios(category: "Actions", component: "Button") {
            Scenario("Primary") { DemoButton(title: "Continue", style: .primary) }
        }
    }
}
    then one line per component ties them together: SwiftBoard.shared.addScenarios(from: [DemoButton.self, DemoBadge.self]). Adding a component means adding one line to that list, not growing a central file.
  • Data-driven, from an existing catalog. If you already have a structured array of component/variant data — like SwiftDS's DSComponentCatalog — map it once into the data-driven addScenarios(category:component:scenarios:) overload. This is what SwiftDSCatalogRegistrar does for SwiftDS's ~40 entries; it scales to hundreds without a hand-written call per state.

Documenting a component (so the board isn’t just pictures)

The site does not inspect your SwiftUI view. Description, initializer parameters, and the code snippet under each card are whatever you pass when you register. If you omit them, the board still lists the named states and a hint to add docs.

board.addScenarios(
    category: "Actions",
    component: "Button",
    summary: "Primary tappable action.",
    parameters: [
        ScenarioParameter(name: "title", type: "String", description: "Label on the button."),
        ScenarioParameter(name: "style", type: "Style", defaultValue: ".primary")
    ]
) {
    Scenario("Primary", docs: ScenarioDocs(snippet: "DemoButton(title: \"Continue\", style: .primary)")) {
        DemoButton(title: "Continue", style: .primary)
    }
}

summary and parameters show in the panel above the cards. ScenarioDocs(snippet:) shows as the example under that state. Put this next to the component (the same file as a #Preview) so the design system owns the copy, not the website.

Modifying an existing component

Edit the SwiftUI view code inside the Scenario's closure (or the underlying component's own source, if the scenario just wraps one). Since this is compiled Swift, not a script, there's no live-reload: stop the running process, rebuild/run again (swift run ... or ⌘R in Xcode), then reload the browser tab.

Removing a component

Delete or comment out its addScenarios call and restart. There is no persisted registry to clean up — the board only exists in memory for the life of the running process; every run starts from nothing and re-registers whatever your code calls.

Native gallery view (no server required)

This site is a website. If you'd rather show the same registered scenarios inside your own app, natively — no HTTP server, no SwiftBoardServer/FlyingFox dependency at all — use BoardGallery, a plain SwiftUI view that lives in the base SwiftBoard target:

import SwiftBoard

.sheet(isPresented: $showGallery) {
    BoardGallery() // reads SwiftBoard.shared by default
}

It reads the exact same registry this site reads, so one addScenarios call feeds both — but here each state renders as your actual live SwiftUI view, not a snapshot image. This is the equivalent of Playbook's in-app gallery/catalog, or of SwiftDS's own DSShowcaseRoot — generic, driven by whatever you've registered.

Previewing on iOS (not just macOS)

SwiftBoardDemo and SwiftBoardKitDemo are plain macOS processes (swift run just runs a binary on your Mac) — fine for the website, but if your design system targets iOS, a macOS process renders SwiftUI with macOS's chrome (fonts, control styles), not iOS's. That's misleading for anything that isn't purely custom-drawn.

To see BoardGallery — and this site's snapshots — rendered by a real iOS Simulator instead:

Scripts/run-ios-demo.sh

This builds SwiftBoardiOSDemo from Examples/ (same SwiftDS registration as SwiftBoardKitDemo, hosted in BoardGallery) for the iOS Simulator, hand-assembles it into an installable .app (plain swift run/swift build can't produce one — this repo has no .xcodeproj), installs it, and launches it on your currently booted Simulator. The website it starts is also reachable at http://127.0.0.1:8080 from your Mac — same URL, now genuinely iOS-rendered.

Using the SwiftDS starter

SwiftBoard's published package has no SwiftDS dependency. Maintainers with a sibling SwiftDS checkout can run cd Examples && swift run SwiftBoardKitDemo. In your own app, add both packages and copy Examples/SwiftDSCatalogRegistrar.swift.

Publishing a real, hosted site

The live server only exists while your app/process is running. To get a permanent, deployable site instead:

try await StaticExporter.export(to: URL(fileURLWithPath: "./site"))

This writes a self-contained folder (HTML/CSS/JS + every snapshot PNG) you can deploy anywhere static files are served, or open directly via file://.
