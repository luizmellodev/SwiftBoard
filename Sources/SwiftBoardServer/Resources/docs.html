SwiftBoard

A runtime component gallery. You register scenarios (a component + a named state) in your own Swift code; this site is a live view of whatever is currently registered in the running process — nothing is generated ahead of time, and nothing is stored on disk unless you explicitly export it.

Getting started

1. See it working (zero setup). This repo already has a working demo you can run before writing anything:

cd SwiftBoard
swift run SwiftBoardDemo

Wait for the status text to say Running at http://127.0.0.1:8080, then open that URL — that's this exact site, showing the demo's example components. (Have SwiftDS checked out too? swift run SwiftBoardKitDemo shows the same thing with a real design system.)

2. Point it at your own components. Once you've seen it work:

  • Already have an app? Add SwiftBoardServer as a dependency, write one file that calls SwiftBoard.shared.addScenarios(...), and call it plus BoardServer().start() from your app's startup code behind #if DEBUG. Run your app as usual and open the URL from the console.
  • Nothing yet, just trying this out? swift package init --type executable in a new folder, add SwiftBoardServer as a dependency, put the two calls above in main.swift followed by RunLoop.main.run(), then swift run.

See this repo's README.md for the exact code for both paths. That one-file example is for getting a single component on screen — once you have more than a couple, see "Creating a new component / state" below for a pattern that scales to a whole design system without growing one giant file.

Where does this code live — my app, or a separate package?

Either. SwiftBoard doesn't require a specific project layout — it only cares that SwiftBoard.shared.addScenarios(...) gets called before BoardServer().start(). Two common setups:

  • No separate design-system package: add the SwiftBoard package as a dependency of your app, write your scenario registrations in a small file (e.g. BoardScenarios.swift) compiled only in DEBUG, and call BoardServer().start() from your app's startup code behind #if DEBUG. Nothing new to create.
  • You already have (or want) a separate design-system package — like SwiftDS in this repo's SwiftBoardKit target: the design-system package itself doesn't need to know SwiftBoard exists. A small bridge target/app (living wherever is convenient — inside that package, inside your app, or standalone) depends on both, registers the design system's components, and starts the server. This is exactly the pattern SwiftBoardKit demonstrates for SwiftDS.

Creating a new component / state

Call addScenarios anywhere that runs before the server starts:

SwiftBoard.shared.addScenarios(category: "Actions", component: "Button") {
    Scenario("Primary") {
        Button("Continue") {}.buttonStyle(.borderedProminent)
    }
    Scenario("Disabled") {
        Button("Continue") {}.buttonStyle(.borderedProminent).disabled(true)
    }
}

Each Scenario is one state/card on the site. Calling addScenarios again for the same category/component appends more states to it. Don't pile every component into one file as your design system grows, though — two ways to keep it manageable:

  • Co-located, one file per component (recommended default). Conform the component's own type to BoardScenarioProvider, right in the file where it's already defined — like a #Preview block: 
    extension DemoButton: BoardScenarioProvider {
    static func provideScenarios(into board: SwiftBoard) {
        board.addScenarios(category: "Actions", component: "Button") {
            Scenario("Primary") { DemoButton(title: "Continue", style: .primary) }
        }
    }
}
    then one line per component ties them together: SwiftBoard.shared.addScenarios(from: [DemoButton.self, DemoBadge.self]). Adding a component means adding one line to that list, not growing a central file.
  • Data-driven, from an existing catalog. If you already have a structured array of component/variant data — like SwiftDS's DSComponentCatalog — map it once into the data-driven addScenarios(category:component:scenarios:) overload. This is what SwiftDSCatalogRegistrar does for SwiftDS's ~40 entries; it scales to hundreds without a hand-written call per state.

Modifying an existing component

Edit the SwiftUI view code inside the Scenario's closure (or the underlying component's own source, if the scenario just wraps one). Since this is compiled Swift, not a script, there's no live-reload: stop the running process, rebuild/run again (swift run ... or ⌘R in Xcode), then reload the browser tab.

Removing a component

Delete or comment out its addScenarios call and restart. There is no persisted registry to clean up — the board only exists in memory for the life of the running process; every run starts from nothing and re-registers whatever your code calls.

Native gallery view (no server required)

This site is a website. If you'd rather show the same registered scenarios inside your own app, natively — no HTTP server, no SwiftBoardServer/FlyingFox dependency at all — use BoardGallery, a plain SwiftUI view that lives in the base SwiftBoard target:

import SwiftBoard

.sheet(isPresented: $showGallery) {
    BoardGallery() // reads SwiftBoard.shared by default
}

It reads the exact same registry this site reads, so one addScenarios call feeds both — but here each state renders as your actual live SwiftUI view, not a snapshot image. This is the equivalent of Playbook's in-app gallery/catalog, or of SwiftDS's own DSShowcaseRoot — generic, driven by whatever you've registered.

Using the SwiftDS starter (SwiftBoardKit)

SwiftBoardKit and SwiftBoardKitDemo are two extra targets that already live inside this same SwiftBoard repository — they are not a separate package, a plugin, or a feature flag you toggle on. A Swift package doesn't have an "enable this target" switch; you simply choose which target to build, run, or depend on.

  • Just want to browse SwiftDS standalone? From this repo: swift run SwiftBoardKitDemo. In Xcode, open this package and pick "SwiftBoardKitDemo" from the scheme picker, then Run.
  • Want it inside your own app instead? Depend on the SwiftBoardKit product (not just SwiftBoardServer) from your app's Package.swift, then call the registrar it exposes followed by BoardServer().start() from your own code.
Depending on SwiftBoardKit pulls in SwiftDS as a transitive dependency, even if your app only uses a couple of its components elsewhere. If you don't want that, stick to the plain SwiftBoard/SwiftBoardServer products and register your own views instead.

Publishing a real, hosted site

The live server only exists while your app/process is running. To get a permanent, deployable site instead:

try await StaticExporter.export(to: URL(fileURLWithPath: "./site"))

This writes a self-contained folder (HTML/CSS/JS + every snapshot PNG) you can deploy anywhere static files are served, or open directly via file://.
